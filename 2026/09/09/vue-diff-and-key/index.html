虚拟 DOM diff 算法与 key 的正确用法

使用 Vue 或 React 时，几乎每个人都写过这样的代码，也几乎都被编辑器警告过：

Elements in iteration expect to have ‘v-bind:key’ directives.

于是 key 变成了一种”加上就不报错”的咒语。但追问几个问题，很多人就答不上来了：

key 到底参与了什么过程？为什么不能用 index 当 key？为什么 Math.random() 当 key 反而更糟？

这些问题全部指向同一个东西：diff 算法。

本文先看 diff 为什么存在、做了哪些简化，再看 Vue2 的双端比较和 Vue3 的最长递增子序列，最后回到 key 的正确用法。

一、diff 解决了什么问题

框架普遍采用虚拟 DOM 的更新方式：

之所以如此在意 DOM 操作的数量，是因为创建和修改真实 DOM 的代价远高于操作普通 JS 对象——前者可能引发样式计算、布局、绘制，后者只是内存中的属性读写。所以一次典型的更新流程是：

diff 本质上是一个性能优化手段：用廉价的 JS 计算换昂贵的 DOM 操作。

顺带回答一个问题：为什么不把两棵树做完整的对比？因为任意树结构的最优对比（树编辑距离）时间复杂度是 O(n³)，1000 个节点就是十亿级别的比较，完全不可用。所以 Vue 和 React 都基于对真实页面更新模式的观察做了几个经验假设，把复杂度降到了线性 O(n)——就是下面这三条策略。

二、diff 的三条基本策略

1. 只做同层比较

diff 只比较同一层级的节点；跨层级的移动会被当作”旧位置删除 + 新位置创建”，而不是”移动”：

这看起来不够聪明，但背后的判断是：真实页面中跨层级移动节点是极少见的，为极少见的场景把复杂度抬回 O(n³)，不划算。

2. 类型不同，直接重建

diff 不会对比 <div> 和 <span> 内部的差异，而是删除旧子树、创建新子树。理由同样来自经验：不同类型的元素渲染出的内容通常完全不同，细对比不如重建。

3. 用 key 标识节点

key 用来回答 diff 中最关键的问题：

新列表里的这个节点，是不是旧列表里那个节点的”同一个”？

注意一个容易忽略的点：key 是节点身份的一部分，而不是附加属性——key 不同，哪怕标签、内容全都一样，也会被认为是两个不同的节点。

这三条策略合在一起，把”任意的树对比”简化成了”同层级的线性扫描”。

三、没有 key 的世界：就地复用

先看反例：如果不写 key，diff 会怎么做？

没有 key 时，Vue 对子节点采用就地复用（in-place patch）：按索引一一配对——不看节点是谁，只看排在第几个。

对于”纯展示、顺序永远不变”的列表，这样效率非常高。但一旦发生头部的增删、排序、过滤，问题就来了。比如列表从 A B C 变成 B C（头部删除了 A）：

本来只需要”删掉第一个节点”，现在变成剩下每个节点都要 patch 一遍，还要多删一个节点。

key 要解决的，正是这个问题。

四、key 到底是什么

有了前面的铺垫，可以给 key 一个准确的定义：

key 是 vnode 的身份标识，diff 用它在新旧两组子节点之间建立配对关系。

key 带来的能力有两个：复用（相同 key 的节点只做增量更新，而不是销毁重建）和移动（位置变化被识别为”移动”，而不是”删除 + 新建”）。

这也决定了 key 必须满足两个条件：

key 不是给开发者看的，是给 diff 算法做节点匹配用的。

五、Vue2 的 diff：双端比较

Vue2 对新旧两组子节点做 diff 的核心函数是 updateChildren()，它维护四个指针：旧头 oldStartIdx、旧尾 oldEndIdx、新头 newStartIdx、新尾 newEndIdx。

每一轮比较，按顺序尝试四种配对：

比如旧 [A, B, C] 新 [B, C, A]：头头 B vs A 不命中、尾尾 C vs A 不命中、旧头 A 对上新尾 A 命中——A 被移到了末尾，正好走第三条路径。四种命中共用一个前提：sameVnode() 成立（key 相同 + 标签相同）。

四次都没命中时（乱序场景），用 key 建索引表兜底：

拿新头节点的 key 去查：查得到 → patch 并移动到旧头之前；查不到 → 是全新节点，直接创建插入。

没有 key，keyMap 无从建起，兜底路径整个失效。

循环结束的条件是某一侧头指针越过尾指针，之后多退少补：旧的先用完 → 批量创建新增节点；新的先用完 → 批量删除多余节点。

六、Vue3 的 diff：预处理 + 最长递增子序列

Vue3 重写了这部分算法（patchKeyedChildren），思路变成：

预处理

很多真实场景（尾部追加、头部删除）在预处理阶段就直接消化完了，根本走不到复杂逻辑。这两步借鉴自 ivi / inferno 两个库。

乱序部分与最长递增子序列

对剩余部分，先为新节点建立 keyToNewIndexMap（key → 新索引），再遍历旧节点：能查到 → patch，记录”新索引 → 旧索引”；查不到 → 删除。

最精妙的一步是根据这个数组求最长递增子序列（LIS）。举例：

数组 [4, 5, 1, 2, 3] 的最长递增子序列是 [1, 2, 3]（对应 A、B、C），含义是：A、B、C 在新旧列表中的相对顺序没有变化。于是 Vue3 的决策是：

递增子序列内的节点相对顺序已经正确，不需要任何移动；剩下的节点插入到正确位置即可——这样把 DOM 移动次数降到最少。

两代实现的对比：

Vue2 Vue3
核心策略 双端比较 预处理 + key 映射 + LIS
快速路径 头尾四次比较 头部 / 尾部同步
乱序处理 keyMap 找到就移动 LIS 保证只移动必须移动的
移动次数 较优 理论最优

注意：两者的匹配依据没有变，都是 sameVnode = key 相同 + 标签相同；变的是”找到匹配之后，如何安排移动”的策略。

八、比 index 更糟：随机数作 key

既然 key 要唯一，那 :key="Math.random()" 行不行？不行，而且比 index 更糟。

Math.random() 每次渲染都会生成新值，导致新列表的每个 key 在旧列表中都查不到，全部被判定为”全新节点”——每次更新都是整个列表删除 + 重建。

后果：diff 的复用能力完全归零（每次更新等价于重渲染整个列表），且所有节点内部状态全部丢失——输入框被清空、组件被重新 mounted、过渡动画从头播放。

十一、React 中的 diff 与 key

同样的思想也适用于 React：reconciliation 同样基于”类型不同重建 + 同层比较 + key 标识”的假设，用法也是 <li key={item.id}>，index 作 key 的后果也一致（头部插入元素时状态错位、输入框内容张冠李戴）。

实现层面的差异主要在”乱序部分的移动策略”：

React 不做双端比较，从左到右遍历新列表，用”最后一个已放置节点的位置”判断当前节点是移动还是原地复用；对乱序程度高的列表，移动次数通常多于 Vue3。

对这些差异，理解到这一层就够了：

不同框架的 diff 策略有差异，但 key 的语义完全一致——节点身份标识。

十二、总结

把全文的主线串起来：

key 的正确用法，浓缩成一张表：

key 写法 唯一 稳定 结果
item.id ✓ ✓ 复用 + 最少移动，正确且高效
index ✓ ✓ 位置不指向数据：patch 放大、状态错位
Math.random() ✓ ✗ 每次渲染全量重建，状态全丢
不写 key — — 就地复用：乱序场景下问题同 index

最后回到那个根本问题——key 是什么？

key 是给 diff 算法看的节点身份证：diff 靠它在新旧列表之间配对节点，从而做到”能复用的不重建，能不动的少移动”。

身份证的要点从来只有两个：唯一，且始终属于同一个人。
