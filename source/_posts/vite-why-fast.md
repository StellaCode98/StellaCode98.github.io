# Vite 为什么那么快

"Vite 快"是所有人的第一体感：冷启动从分钟级变秒级，改一行代码浏览器几乎瞬间刷新。但 Vite 快在哪，答案不是"优化做得好"，而是**架构上少做了事**。

一句话先给结论：

> **Webpack 的开发服务器先把整个应用打包成 bundle 再启动；Vite 开发态根本不打包——把模块加载交还给浏览器（原生 ESM），把依赖处理交给 esbuild，自己只做按需编译。**

---

## 一、先看 Webpack 慢在哪：慢是结构性的

Webpack dev server 的工作方式：

```text
启动 → 从入口递归解析整个依赖图 → 逐模块 transform → 打包成 bundle → 启动服务
```

问题在这两件事上：

- **冷启动与项目规模成正比**。模块从 100 个涨到 5000 个，启动时间跟着线性涨——哪怕你这次只改一个小功能，也得等全量打包完。
- **HMR 也随规模变慢**。热更新虽然只改一个文件，但要重新打包受影响的 chunk、重新拼接模块注册表，项目越大这笔开销越大。

也就是说，慢的根源是：**"打包"这个动作发生在启动时，而打包的工作量天生与项目规模挂钩**。

## 二、Vite 的核心答案：开发态不打包

现代浏览器原生支持 ESM。`import` 一个模块，浏览器会自己发请求去拿：

```html
<script type="module" src="/src/main.ts"></script>
```

Vite dev server 做的事变成：

```text
启动 server（秒级，与业务代码量无关）
浏览器请求 main.ts → Vite 拦截，实时编译这一个文件返回
浏览器执行到 import App.vue → 再发请求 → 再编译这一个文件
……用到哪个模块，才编译哪个模块
```

Webpack 在**构建期**一次性解析的整棵依赖图，被 Vite **推迟到浏览器运行时按需发生**。首屏只编译首屏用到的代码，没访问到的路由、没引入的组件，编译成本为零。

代价是首次访问某页面时有零星按需编译的等待，但换来的是冷启动与项目规模**解耦**。

## 三、依赖为什么还要预打包：esbuild 登场

业务代码可以按需编译，但 `node_modules` 里的依赖不行，两个原因：

1. **格式问题**：React 等大量依赖是 CommonJS，浏览器原生 ESM 吃不下，必须转成 ESM。
2. **请求问题**：`lodash-es` 有几百个小模块文件，不合并的话浏览器会发起几百个请求，嵌套 import 还会层层瀑布。

所以 Vite 启动时用 **esbuild** 把依赖预打包：CJS 转 ESM + 几百个小文件合并成少数几个：

```text
node_modules/lodash-es/**（几百个文件）
        ↓ esbuild 预打包
node_modules/.vite/ 下的一两个文件 → 强缓存，后续不再处理
```

选 esbuild 是因为它是 Go 编写的原生二进制，多核并行、不做类型检查，比 JS 写的工具快 10~100 倍——预打包这一步再快也不过是"用最快的引擎做一次最少的活"。

而且预打包结果**强缓存**在 `node_modules/.vite`，只有 lockfile 或 Vite 配置变化才重新打包，二次启动这部分成本接近零。

## 四、HMR 为什么与项目规模无关

```text
编辑文件 → 服务端只重新编译这一个模块
        → 沿模块图向上找到 HMR 边界（通常是一个组件）
        → 浏览器只替换这个组件，页面状态不丢
```

整条链路的工作量 = 一个模块的编译 + 局部替换，**与项目有多少个模块无关**。Webpack 时代"项目越大、保存越慢"的体验问题被架构性消除，而不是被优化缓解。

## 五、网络层的两个细节

- **依赖**：`Cache-Control: max-age=31536000, immutable`，内容变即换文件名，浏览器连协商请求都不发。
- **源码**：`ETag` 协商缓存，没改过的模块 304 直接用，改过的才重新编译传输。

配合按需编译，这套缓存让"改一行、刷一次"的实际传输量只有一两个文件。

## 六、生产构建为什么不用同一套

如果生产也直接用原生 ESM 按需加载行不行？不行：

- 嵌套 `import` 在真实网络下会形成请求瀑布，首屏性能不可接受；
- 不打包就无法 tree shaking、无法合并压缩、无法兼容旧浏览器。

所以 Vite 生产构建仍然用 **Rollup 全量打包**（内核就是 Rollup）。这也解释了[《Vite vs Webpack：迁移成本与收益评估》](/2026/09/10/vite-webpack-migration/)的结论：**Vite 的收益几乎全在开发态，生产构建未必更快**。2026 年的补充是 Rust 重写的 Rolldown 正在统一 esbuild + Rollup 双引擎，但"开发不打包、生产打包"的架构分层没有变。

---

## 总结

| 维度 | Webpack dev | Vite dev |
| --- | --- | --- |
| 冷启动 | 全量打包后启动，随规模线性变慢 | 启服务 + esbuild 预打包依赖，与业务规模无关 |
| 页面加载 | 一次性加载 bundle | 原生 ESM 按需请求、按需编译 |
| 依赖处理 | 进 bundle | esbuild 预打包 + 强缓存 |
| HMR | 重打受影响 chunk，随规模变慢 | 单模块编译 + 边界替换，与规模无关 |
| 生产构建 | 打包 | 一样是打包（Rollup） |

**本质**：Vite 的快，不是把打包这件事做得更快，而是想清楚了"什么时候做什么事"——开发态把模块解析还给浏览器、把依赖交给 esbuild，生产态该打包还是打包。快是架构分层的红利，不是引擎调优的红利。
